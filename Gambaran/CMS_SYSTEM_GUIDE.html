Ringkasan dalam satu paragraf

CTC adalah aplikasi web internal untuk mengelola siklus hidup container (CT) kereta milik Baracoal: mencatat container naik/turun gerbong setiap hari, melaporkan kerusakan lewat inspeksi, menyerahkan container ke vendor perbaikan lewat BAST 1 (ke Vendor) dengan approval berjenjang, memantau progress perbaikan, menerima kembali container lewat BAST 2 (dari Vendor) sambil menghitung masa garansi dari kontrak, sampai scrap container yang tidak layak. Setiap transaksi mengikuti pola DRAFT → POSTED → APPROVE, dan setiap perpindahan status mengubah status container serta mengirim email (dan WhatsApp untuk inspeksi) ke role terkait.

Teknologi

  • Backend: Laravel 8, PHP 8.1-FPM, pola Controller → Repository → Model
  • UI: Blade + Livewire 2 (form detail), CoreUI 4, Yajra DataTables, Livewire Charts
  • Database: SQL Server (query memakai TRY_CAST, ISNULL) + view v_ct_*
  • Excel: maatwebsite/excel (import aktivitas harian, export report)
  • Notifikasi: Laravel Mail (15 Mailable) + WA gateway HTTP 172.16.10.114:3000
  • Deploy: Deployer → 172.16.10.28:/var/www/html, branch main

Pengguna (8 role, app/Enums/RoleEnum.php)

  • Administrator: semua menu & master data; lolos semua cek role
  • Checker: input aktivitas harian, inspeksi, BAST 1/2, progress
  • Supervisor: approve inspeksi, BAST 1 tahap 1, BAST 2, progress; buat scrap
  • Manager: approve BAST 1 tahap 2, approve scrap
  • Finance: approve BAST 1 tahap 3
  • Finance Staff, Purchasing, Site Manager: lihat data (read-only)

1Arsitektur & cara sistem berjalan

Siklus sebuah request

  1. User membuka / → diarahkan ke /console/login (routes/web.php). Login memakai username + password dari tabel admins dengan guard admin (C/Auth/LoginController.php:31).
  2. Semua route aplikasi berada di grup auth:admin pada routes/admin.php, diberi prefix /console oleh app/Providers/RouteServiceProvider.php:49.
  3. Tiap route diberi middleware role:A,B,C → app/Http/Middleware/RoleMiddleware.php memanggil Admin::hasRole() (M/Admin.php:50). Administrator selalu lolos. Jika role tidak cocok → HTTP 403.
  4. Controller memanggil Repository (mis. InspectionRepository::posted()). Repository membuka DB::beginTransaction(), mengubah status transaksi, mengubah status container, mengirim email, lalu DB::commit().
  5. Halaman detail transaksi memuat komponen Livewire untuk menambah baris detail (pilih container, upload foto, isi item pekerjaan). Aturan "container mana yang boleh dipilih" ada di sini, bukan di repository.
  6. Daftar (index) memakai Yajra DataTables di app/DataTables/; query-nya di getDataTableQuery() masing-masing repository.

Hal penting tentang cara kerja

Semua proses dipicu user. Tidak ada scheduler/cron. Pekerjaan "otomatis" hanya berjalan ketika halaman tertentu dibuka:
  • Buka Dashboard → cek status sesi WA; jika putus → config whatsapp-notif dimatikan + email ke it@baracoal.com (C/DashboardController.php:20).
  • Buka daftar Aktivitas Harian → draft > 7 hari dihapus (C/ContainerDailyActivityController.php:19 → R/ContainerDailyActivityRepository.php:131).
Email ber-ShouldQueue tapi queue = sync. Semua 15 class di app/Mail mengimplementasikan ShouldQueue, tetapi .env.example memakai QUEUE_CONNECTION=sync. Artinya email dikirim langsung di dalam DB transaction; bila SMTP gagal, proses POST/approve ikut gagal. Cek nilai .env di server produksi.

4Alur proses end-to-end

Narasi alur

  1. Container turun dari rangkaian. Checker membuat Aktivitas Harian jenis Turun Container (manual atau upload Excel). Saat POST, CT menjadi TSO (atau SO di BJI/BBA) dan lokasi/gerbong/waktu turun dicatat di tabel containers.
  2. Kerusakan dilaporkan. Checker membuat Inspeksi, menambah detail per CT berisi deskripsi kerusakan, penyebab, dan foto. POST → CT menjadi TSO/TSOI, email ke semua Supervisor, laporan ke grup WA.
  3. Supervisor menilai. Supervisor mengisi jenis perbaikan (Maintenance / Upgrade & Repair) dan root cause tiap detail, lalu Approve → containers.last_type_maintenance diisi; Reject → kembali DRAFT + email ke Checker.
  4. CT diserahkan ke vendor (BAST 1). Checker memilih vendor, kontrak, lokasi dan jenis pekerjaan; detail = CT yang pernah diinspeksi dan berstatus TSO/TSOI. Sub-detail (item pekerjaan) otomatis dibuat dari detail inspeksi yang belum dipakai, lalu diisi harga dari kontrak. Approval berjenjang Supervisor → Manager → Finance.
  5. Vendor memperbaiki. Checker membuat Progress Perbaikan per vendor + lokasi; sistem menarik semua CT di BAST 1 yang belum selesai (is_done = 0). Progress (%) tidak boleh turun. Supervisor approve.
  6. CT kembali (BAST 2). Checker membuat BAST dari Vendor; detail diambil dari BAST 1 yang belum selesai dan wajib punya progress yang sudah POSTED. POST → progress dipaksa 100%. Supervisor approve → garansi dihitung, BAST 1 ditandai selesai, CT menjadi SO.
  7. CT dinaikkan lagi. Aktivitas Harian Naik Container → CT O. CT TSO yang masih punya BAST 1 belum selesai ditolak untuk dinaikkan.
  8. Jalur alternatif — Scrap. CT TSO yang tidak layak diperbaiki diajukan Supervisor; Manager approve → CT S.

6BP-02 · Aktivitas harian container

Tujuan: mencatat pergerakan CT setiap hari (naik/turun gerbong, bongkar truk) yang menentukan status operasional CT. Pelaku: Checker (input, POST). Tidak ada approval.

Langkah

  1. Buat header: lokasi, tanggal aksi, jenis (C/ContainerDailyActivityController.php:30 store).
  2. Tambah detail per CT: jenis aktivitas, CT, no. gerbong, no. trainset, sumber CT (L/ContainerDailyActivity/FormDetail.php:175 submit) atau upload Excel kolom ct_no, container_source, carriage_number, type (:220 upload → app/Imports/ContainerDailyActivityDetailsImport.php, file disimpan di storage/bba-activity-files).
  3. POST → status CT berubah sesuai tabel transisi (bagian 3) + kolom down_location_id / down_carriage_no / down_at atau up_* diperbarui (R/ContainerDailyActivityRepository.php:26 posted).

Aturan bisnis

  • Dropdown CT difilter per jenis aktivitas (FormDetail.php:79 updatedType): Turun = TSO (atau O/TSO di BBA/BJI) yang sedang naik dan tidak ada di draft lain; Naik = SO/TSO/SOI; Putus Gerbong = O; CT-DT = SO/O; Truck Unloading & Uplift = SO; Container Unloading = TSOI.
  • Naik Container ditolak jika CT TSO masih punya detail BAST 1 dengan is_done = 0 (FormDetail.php:154).
  • Satu CT hanya boleh sekali per transaksi (rule unique). Draft > 7 hari dihapus otomatis saat daftar dibuka.
